# Voyeger Frontend Redesign — Backend Coordination Proposal (Phase 4)

This document lists minimal, optional backend improvements identified during the frontend redesign. **No backend files or contracts were modified during the frontend redesign**; the frontend runs completely against the existing `docs/API_CONTRACT.md` specification.

| # | Area | Existing Schema / Endpoint | Gap | Proposed Minimal Change | MVP Mandatory? | Frontend Impact |
|---|---|---|---|---|---|---|
| 1 | Discovery vs Content Type | `places.json` uses one `category` enum (`hidden_gem`, `food`, `culture`, `experience`) plus `is_anchor: boolean`. | A non-anchor local food or cultural spot cannot simultaneously be tagged as a `hidden_gem` without losing its type. | Add an optional `discovery_tier?: "anchor" \| "hidden_gem" \| "standard"` (or `is_hidden_gem?: boolean`) alongside `category` in YAML schema and `places.json`. | No | `MapCanvas` & filters currently respect `category === "hidden_gem"` for the Hidden Gems chip and `!is_anchor` for zoom-13+ reveal and XP (`anchor=10`, `food=20`, other non-anchor=30). Adding a dedicated field allows filtering hidden food/culture gems cleanly. |
| 2 | Destination Theme Palette | `Place.theme` is optional in frontend types; currently omitted in `v1`/`v2` pack output. | All destination pages without `theme` fall back to Voyeger brand colours (`--primary`, `--secondary`). | Allow optional `theme: { primary, secondary }` in content YAML and validate hex/OKLCH format in `pipeline.validate`. | No | `PlacePage` already reads `place.theme?.{primary,secondary}` with automatic brand fallback and readable card contrast. |
| 3 | Partner Photo Upload | `POST /api/partners/apply` accepts JSON `{ id, name, type, contact, offer, place_ids, created_at }`. | Community partners cannot attach photos with applications yet. | Add `POST /api/partners/apply/media` (multipart upload returning media reference) or `photo_urls?: string[]` field after moderation workflow is ready. | No | `PartnersPage` marks photo upload as a **planned future integration** and sends the exact JSON contract via outbox. |
| 4 | User Discovery / XP Sync | Discovery XP lives locally in Dexie `discoveries` table (`placeId`, `category`, `isAnchor`, `xp`, `discoveredAt`). | Progress stays on-device across sessions; not synced across devices. | Optional anonymous device progress endpoint (or include discovery milestones in telemetry) if cross-device sync is needed later. | No | Zero breaking impact; local Dexie `discoveries` remains authoritative offline. |
| 5 | Offline Map Archive | Frontend requests `/tiles/bhopal.pmtiles` with HTTP Range requests (`vite.config.ts` caches `map-tiles-v1`). | Repository contains `public/tiles/README.md` placeholder without `bhopal.pmtiles`; fallback uses online OSM raster tiles when reachable. | Generate/host Bhopal vector PMTiles archive at `/tiles/bhopal.pmtiles` on backend static mount or in `public/tiles/`. | Recommended before field use offline | Zero code changes needed once `bhopal.pmtiles` (`tileType === 1` vector PMTiles) is placed at `/tiles/bhopal.pmtiles`. |
| 6 | Static Phrasebook Review | Static 5-language (`en`, `hi`, `ta`, `bn`, `mr`) travel phrasebook bundled in `src/features/translate/phrasebook.ts`. | Draft non-English translations carry `needs_review: true`. | Native-speaker verification and optional pack-delivered phrasebook JSON (`/pack/v{N}/phrasebook.json`). | Recommended | Zero code change needed to flip `needs_review` once reviewed. |
